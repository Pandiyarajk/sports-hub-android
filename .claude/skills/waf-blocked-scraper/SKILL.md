# waf-blocked-scraper

A WAF sitting between your HTTP client and a site. The reason this needs a skill
is that **the block does not look like a block**: the tool exits 0, the body is
valid HTML, and the parser reports "nothing found" rather than "refused". The
usual reflex — bolt on a full set of browser headers and move on — often fixes
it for the wrong reason and leaves you believing something false about the site.

Headers cannot beat a JavaScript challenge; when you hit one, drive a real
browser instead ([browser-smoke-test](../browser-smoke-test/SKILL.md)).

## When to use

- A fetch "succeeds" but the file is a few hundred bytes, or every selector is
  empty.
- A Python client gets `403`/`406` on a URL that loads fine in a browser.
- A scraper that worked for months starts returning nothing after a dependency
  bump or a "cleanup" that touched the request.
- Someone fixed it by adding browser headers and nobody knows which one mattered.
- A request fails only *sometimes*, or fails on startup and works after a retry —
  that is volume, not identity (§7).
- Failures arrive suspiciously fast, or get worse the more you retry.

## 1. Get the status and the size before theorising

`curl -s` exits **0** on a 403 or a 406. Nothing in the shell tells you the
request was refused, and the block page is well-formed HTML, so `grep`, an HTML
parser and a JSON decoder all fail quietly downstream instead of loudly here.

```bash
curl -sL --max-time 45 -o out.html -w "status=%{http_code} wire=%{size_download}\n" "$URL"
wc -c < out.html
```

Two traps in that one line:

- **Never judge by exit code.** Use `-w "%{http_code}"`, or `--fail` if you want
  a non-zero exit on 4xx/5xx.
- **`%{size_download}` is the wire size.** With `--compressed` it reported
  `42891` for a page that was `256346` bytes on disk. Check the file.

Then fingerprint what came back:

| Body | Status | Who | What it means |
|---|---|---|---|
| `Not Acceptable!` … `generated by Mod_Security`, ~226 bytes | 406 | ModSecurity / OWASP CRS on Apache | A request-**header** rule fired |
| `error code: 1010`, 17 bytes | 403 | Cloudflare | "Browser signature banned" — your User-Agent |
| `Just a moment…` / `Attention Required!`, JS + `cf_chl` | 403/503 | Cloudflare bot management | A challenge; headers will not fix it |
| `Making sure you're not a bot!`, `anubis_challenge` JSON, ~4.4 KB | **200** | Anubis (proof-of-work) | A challenge that does **not** look like an error: status checks pass |
| A framework error page (ASP.NET yellow screen, Rails trace) | 500 | The **origin**, not a WAF | Your parameters, not your headers |

That last row matters: an origin 500 with a plausible-looking body sends people
header-hunting for hours. If the page names your framework, the WAF let you
through.

### A 200 is not proof you got the file

Anubis answers with **HTTP 200** and `text/html`. A status check, `curl --fail`
and PowerShell's `Invoke-WebRequest` (which throws only on 4xx/5xx) all pass,
and `-OutFile` writes the challenge page under whatever name you gave it.
Observed Nov-12-2026 on `fedorapeople.org`:

```powershell
Invoke-WebRequest -Uri https://fedorapeople.org/.../virtio-win-guest-tools.exe -OutFile virtio-win-guest-tools.exe
# no error. File: 4,444 bytes, HTML. Get-AuthenticodeSignature: Status = UnknownError
# re-requested: status=200 type=text/html; charset=utf-8 title="Making sure you're not a bot!"
```

When you download a binary, check what arrived, not the status code: the
`Content-Type`, the size against what you expect, the first bytes (`MZ` for a
Windows executable, `PK` for a zip), and for a signed installer
`Get-AuthenticodeSignature` reading `Valid`. A proof-of-work challenge is meant
to stop automated clients: don't solve it in code. Fetch the file through a
real browser, or find another official copy. In that case the virtio-win ISO
was already on the cluster's shared ISO storage.

## 2. Bisect the request — one header at a time

The most common wrong conclusion is *"bare requests are blocked."* Test it
rather than assuming it. A probe loop costs thirty seconds and replaces the
whole theory:

```bash
probe() { printf '%-52s -> ' "$1"; \
  curl -sL --max-time 45 -H "User-Agent: $2" -o /dev/null -w "%{http_code}\n" "$URL"; }

printf '%-52s -> ' "(client default, nothing set)"; curl -sL -o /dev/null -w "%{http_code}\n" "$URL"
probe "Mozilla/5.0"                              "Mozilla/5.0"
probe "Mozilla/5.0 (Windows NT 10.0; Win64; x64)" "Mozilla/5.0 (Windows NT 10.0; Win64; x64)"
probe "full Chrome UA"                           "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/128.0.0.0 Safari/537.36"
probe "Python-urllib/3.13"                       "Python-urllib/3.13"
probe "python-requests/2.32.3"                   "python-requests/2.32.3"
probe "mytool/0.1 (+https://example.com/x)"      "mytool/0.1 (+https://example.com/x)"
```

Against a live ModSecurity host this produced three different answers and
demolished the obvious reading (full table in **Evidence**):

- **A genuinely bare request was fine.** No UA at all, an empty UA and curl's
  own default all returned the full 256 KB page.
- **`Mozilla/5.0` alone was the block.** A UA that claims to be a browser and
  stops short of one is exactly what a "malformed / fake user agent" rule looks
  for. Adding the parenthetical — `Mozilla/5.0 (Windows NT 10.0; Win64; x64)` —
  returned 200.
- **Library defaults are blocked by name.** `Python-urllib/3.13` → **403**,
  `python-requests/2.32.3` → **406**. Two different status codes means two
  different rules; the urllib one was Cloudflare, the requests one ModSecurity.
- **The rest of the header pile did nothing.** A complete Chrome UA *by itself*
  returned 200. `Accept`, `Accept-Language`, `Sec-Fetch-*` and
  `Upgrade-Insecure-Requests` were never the fix.

## 3. Escalate in order, and stop at the first thing that works

1. **An honest UA naming your tool and a contact URL.** It passed every host
   tested, and it is the only option that stays true if the site later asks who
   you are.
2. **A complete, current browser UA** — if and only if step 1 is blocked.
   Truncated is worse than absent.
3. **The full browser header set** plus `--compressed` — for origins that vary
   on `Accept`/`Accept-Encoding`.
4. **`Referer`** — for images and assets behind hotlink protection, which fail
   independently of the page that worked.
5. **A real browser** — Playwright/headless Chrome — the moment you see a JS
   challenge. No header set solves one.

Two rules regardless of step:

- **One escalation pass, then stop.** Retrying a block in a loop is how a
  transient rule becomes an IP ban.
- **Say which step you are on and why**, in a comment next to the header. The
  next person's "simplification" is what re-breaks this.

## 4. "We don't set a User-Agent" is not the same as "no UA is sent"

`urllib` adds its default at send time, inside `AbstractHTTPHandler.do_open` —
so the header is invisible on the object you built:

```python
req = urllib.request.Request(url)
req.get_header("User-agent")     # -> None ... and the wire carries Python-urllib/3.13
```

Verified against a Cloudflare-fronted portal: that request returned **HTTP 403,
`error code: 1010`** (17 bytes), while the identical request with an explicit
tool UA reached the application and got its ordinary 404. `requests` behaves the
same way with `python-requests/<version>`.

The consequence is worth writing into the code, because a UA line reads like
decoration and deletes cleanly:

```python
# Load-bearing: Cloudflare answers urllib's default Python-urllib/<version> UA
# with HTTP 403 "error code: 1010" (browser signature banned). Do not remove.
USER_AGENT = "gcis/0.1 (+https://github.com/pandiyarajk/gcis)"
```

## 5. Diagnose with the request you are actually debugging

The incident behind this skill produced a wrong diagnosis from a good instinct.
The failing call was a `GET` with `-A "Mozilla/5.0"`; the follow-up probe was
`curl -sIL` with `-A "Mozilla/5.0 (Windows NT 10.0; Win64; x64)"`. It returned
`200 OK`, which read as *"the site is healthy, so bare requests must be blocked"*
— and both halves of that were wrong. The probe had silently changed two
variables at once: the method **and** the UA, and the UA was the whole story.

- Change one variable per probe.
- A `-I`/HEAD result is not a GET result. Confirm with a real GET.
- If a probe contradicts the failure, suspect the probe first.

## 6. Make a block impossible to mistake for empty data

A 226-byte block page parses fine, so "blocked by the WAF" and "no homework
today" become the same output. Fail loudly at the fetch boundary instead:

```python
BLOCK_MARKERS = ("Mod_Security", "error code: 1010", "Attention Required!", "cf_chl")

def _guard(body: str, label: str) -> str:
    """Reject a WAF block page that would otherwise parse as empty content."""
    if len(body) < 2048 or any(marker in body for marker in BLOCK_MARKERS):
        raise PortalError(f"{label}: the site's WAF refused the request (not a content problem)")
    return body
```

Size the floor from the real block page and the real content page — 226 bytes
versus 256 KB leaves a very wide margin. And keep the URL out of that message if
it carries a token in the query string.

## 7. If it varies run to run, it is volume, not identity

Everything above assumes the block is about **who you look like** — the same request
is refused every time until a header changes. A rate limiter behaves the opposite
way: the same request, unchanged, succeeds or fails depending on what else you sent
recently. Bisecting headers against it will "work" and "stop working" at random and
teach you nothing.

Tell them apart before touching a single header:

| | Identity block | Volume block |
|---|---|---|
| Same request, repeated | fails every time | fails sometimes |
| Correlates with | headers, UA, TLS fingerprint | concurrency and recent request count |
| Status | 403 / 406, often a block page | whatever the app returns — **including 404** |
| Timing | varies | conspicuously fast, well under a real response |
| Repeat bursts | unchanged | **gets worse** |

**The status may be an ordinary application code.** `parentsalarmapp.com` answers a
burst with **HTTP 404 in ~0.1 s**, against 0.5–2.4 s for the same module's real
response. Nothing says "rate limit"; there is no `429`, no `Retry-After`. A client
that treats 404 as "this module does not exist" — the obvious reading — reports the
feature as unavailable and moves on.

Measured Aug-22-2026, same host, same headers, only the pattern varied:

| Pattern | Result |
|---|---|
| 6 concurrent | 6/6 ok, 2–3 s each |
| 12 concurrent | 4 failed; repeat 8 failed; repeat again 10 failed |
| sequential, unpaced (12 requests in 5.8 s) | 3 of 12 failed |
| sequential, ~1.0 s apart | 6/6 ok |
| sequential, ~2.0 s apart | 6/6 ok |

Two things follow, and the second is the one people get wrong:

- **It degrades under pressure.** Three back-to-back bursts got monotonically worse,
  and the limiter stayed engaged for roughly two minutes afterwards. Retrying harder
  is not neutral — it is the thing making it fail.
- **Your own probing poisons the next measurement.** After hammering, a *sequential*
  run still lost 3 of 12. Had that been the first experiment, the honest conclusion
  would have been "sequential does not help either", which is false. Cool off before
  re-measuring, and treat any run that follows a burst as unusable.

### Find the pace, then enforce it in one place

Bisect the gap the way §2 bisects headers — 0 s, 1 s, 2 s — and take the smallest
that is clean twice.

Then put it somewhere no caller can bypass. A per-call-site `sleep` is a rule
everyone has to remember; a gate is a rule nobody can forget:

```kotlin
private val gate = Mutex()
private var lastRequestAt = 0L

// Mutex held for the whole request, so every caller is serialised whether it knows
// it or not - including retries, background sync and anything added later.
private suspend fun <T> paced(block: suspend () -> T): T = gate.withLock {
    val since = System.currentTimeMillis() - lastRequestAt
    if (since < MIN_REQUEST_GAP_MS) delay(MIN_REQUEST_GAP_MS - since)
    try { block() } finally { lastRequestAt = System.currentTimeMillis() }
}
```

Retry on top of it, with the backoff growing per attempt, and **split the statuses by
whether waiting can change the answer**:

- **Retry** the throttle status (404 here), 5xx, and IO/timeout.
- **Do not retry** 401/403. A rejected credential will not start being accepted, and
  retrying it three times per module turns one failure into a burst — feeding the
  limiter that caused the problem.

### Where this hides

Fan-out you did not think of as fan-out. The incident behind this section was an app
that refreshed **two children in parallel, six modules each** — twelve concurrent
requests at startup, from code where each half looked entirely reasonable. The symptom
was one module reporting "could not load" on launch and coming right after a few
manual refreshes, which reads as a flaky server rather than self-inflicted load.

Count the requests a cold start actually makes before assuming the server is at fault.

## Evidence

Measured Aug-22-2026 against two live hosts — `greenfieldchennai.com`
(Apache + ModSecurity behind Cloudflare) and `parentsalarmapp.com` (Cloudflare in
front of ASP.NET MVC). Same URL, same method, only the `User-Agent` varied:

| User-Agent | greenfieldchennai.com | parentsalarmapp.com |
|---|---|---|
| *(none set — client default)* | **200**, 255,989 B | 404 *(app's own)* |
| *(empty string)* | **200** | — |
| `Mozilla/5.0` | **406** Mod_Security, 226 B | 404 |
| `Mozilla/5.0 (Windows NT 10.0; Win64; x64)` | **200** | — |
| full Chrome 128 UA, no other headers | **200** | — |
| `Python-urllib/3.13` | **403** | **403** `error code: 1010`, 17 B |
| `python-requests/2.32.3` | **406** | 404 |
| `gcis/0.1 (+https://github.com/pandiyarajk/gcis)` | **200** | 404 *(app's own)* |

The `404 (app's own)` cells above mean the request reached the application — for
*that* URL, which genuinely has no such path. Do not carry the inference further: on
this same host a 404 is also what the rate limiter returns (§7), so "we got the app's
404" proves you passed the WAF and nothing about whether you passed the limiter.

Origin of the incident: `curl -sL -A "Mozilla/5.0" https://greenfieldchennai.com/`
wrote a **226-byte** file, exit **0**, and the follow-up `grep` for logo URLs
printed nothing — which looked like a site with no logos rather than a refused
request. The fix applied at the time (a full browser header set) worked, but §2
shows the header set was never the operative part, and the recorded explanation
— "ModSecurity blocked the bare request" — was the opposite of what the WAF was
doing.
